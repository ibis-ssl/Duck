[前回の報告](https://github.com/ibis-ssl/Duck/pull/84#issuecomment-6405067535)では、Windows の単体テスト 11 件が共有違反で失敗していました。

## 2. 今回分かったこと

Windows の 11 件は、書き込み中のファイルを読み込む際の共有設定が原因でした。
同じプロセス内で書き込み用のファイルを開き、製品の読み込み処理を呼ぶと、3 種類とも共有違反を再現しました。
読み込み側で既存の書き込みを許可する比較処理では、同じファイルを読み込めました。

Docker の停止原因は、事前検査が基底イメージにも `docker image inspect` の成功を要求することでした。
固定した 2 参照のイメージ登録はありませんが、同じ Docker 環境に対応するビルドキャッシュの記録が 6 件ありました。
そのため、イメージ登録がないという結果だけでは、必要なビルド資材もないとは判断できません。

この変更で追加したものは調査報告と証拠です。
製品の実装や単体テストの動作は変更していません。
原因と修正候補を特定しましたが、不具合の解消や実機受入の完了は報告していません。

## 3. 原因と再現条件

### Windows のファイル共有

書き込み側は、次の設定でファイルを開きます。
`Flush()` は書き込み内容を出力しますが、ファイルを閉じる処理ではありません。
ファイルは `Stop()` または `Dispose()` まで開いたままです。

```csharp
new FileStream(capturePath, FileMode.CreateNew, FileAccess.Write, FileShare.Read)
```

一方、3 種類の読み込み処理は `File.ReadLines(path)` を使っています。
Windows でファイルを開くには、新しい読み込み側の共有設定と既存の書き込みが両立することも条件です。
この読み込みでは既存の書き込みを許可できず、`IOException` の `0x80070020` が返ります。
同一プロセス内の複数のファイル操作にも共有条件が適用されます。
仕様の根拠は [Windows のファイル作成 API の公式説明](https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-createfilea)です。

| 読み込み処理 | 失敗した件数 | 対象箇所 |
| --- | ---: | --- |
| 診断記録 | 2 | `DiagnosticsSampleLog.cs:166` |
| 追跡パケット | 6 | `TrackerPacketSnapshotLogReader.cs:38` |
| 追跡結果の対応記録 | 3 | `TrackerSnapshotAlignmentLogReader.cs:27` |

対象ファイルは `Tracker/Tracker.DebugHost/Tracking/` にあります。
例えば `TrackerComparisonSourceTddTests.cs` は、書き込み用の変数を `using var` で保持した状態で読み込む構成です。
85 行目で変数を作り、105 行目で `Flush()` を実行し、変数を破棄する前の 112 行目で読み込みます。
この条件を維持した再実行で、前回失敗した 11 件すべてが同じ例外で失敗しました。
実行結果と例外の呼び出し元は [単体テストの証拠](evidence/issue81-pr84-failure-causes-20261026/focused-results.json)に保存しています。

さらに、現在の製品の `Tracker.DebugHost.dll` を使って、3 種類の読み込み処理を同じプロセス内で比較しました。
ファイルには空行を 1 行だけ入れ、記録の形式とは独立にファイルを開く条件を確認しています。

| 書き込み側の状態 | 読み込み方法 | 3 種類の結果 |
| --- | --- | --- |
| ファイルを保持 | 製品の読み込み処理 | 3 件とも `0x80070020` |
| ファイルを保持 | `FileAccess.Read` と `FileShare.ReadWrite` を明示した比較処理 | 3 件とも読込成功 |
| ファイルを閉じた後 | 製品の読み込み処理 | 3 件とも読込成功 |

9 条件すべてが予測した結果になり、診断処理の終了値は 0 でした。
これは、想定した 3 件の例外と 6 件の読込成功を確認した結果です。
製品の単体テスト 9 件が成功したという意味ではありません。
[再現用プログラム](evidence/issue81-pr84-failure-causes-20261026/SharingCauseProbe.cs)と[比較結果](evidence/issue81-pr84-failure-causes-20261026/probe-result.json)を添付しています。
空行による比較では、並行書き込み中の記録内容や途中の行の扱いまでは検証していません。

共有設定に関係する製品ファイル 5 個は、前回修正前の `f9dc75354a8a3a3216ddf995e232a7685f83203d` と同じ Git オブジェクトでした。
この共有設定の不整合は、前回の 3 指摘対応で追加されたものではありません。
ただし、旧版で Windows の全件テストを再実行したわけではありません。
ファイルごとの比較値は [実装の比較の証拠](evidence/issue81-pr84-failure-causes-20261026/investigation-summary.json)に記録しました。

### Docker の事前検査

`scripts/verify_desktop_referee_acceptance.py` の事前検査は、4 つの固定参照に対して `docker image inspect` を実行します。
ここには、直接起動するイメージに加え、管理対象アプリケーションをビルドするための基底イメージ 2 個も含まれます。
前回は実行環境の基底参照で検査が停止し、終了値は 3 でした。
別に実施した `aspnet` の基底参照の確認も、終了値 1 で失敗しています。

対象の固定参照は次のとおりです。

```text
mcr.microsoft.com/dotnet/runtime@sha256:0cf09aaccf6a9f68900aed4c73fb28fe25bb59ec85de4dea08ba02240a8635f3
mcr.microsoft.com/dotnet/aspnet@sha256:8af87eba5e7cdafb1514d7388be287365da97c132509e84dfe252ffd552398ca
```

今回は読み取りだけで、同じ環境のビルドキャッシュを調べました。
使用中の接続名は `desktop-linux` です。
Docker の識別子は `5bc5ab8a-7340-47ba-8b7c-9f645375a54c` で、前回と一致しています。

```text
docker --context desktop-linux buildx du --builder desktop-linux --format=json
```

このコマンドは終了値 0 で完了しました。
キャッシュの記録 16 件のうち、固定参照に一致した記録は実行環境が 5 件、`aspnet` が 1 件です。
6 件とも `Shared=true`、`Mutable=false` でした。
[該当するキャッシュの記録](evidence/issue81-pr84-failure-causes-20261026/base-cache-records.json)と[実行コマンド](evidence/issue81-pr84-failure-causes-20261026/buildx-cache-command.json)を添付しています。
コマンドが示す内容は [Docker の公式説明](https://docs.docker.com/reference/cli/docker/buildx/du/)に記載されています。

管理対象アプリケーションは、`Testing/Duck.Testing.AppHost/Program.cs` の `WithDockerfile(...)` を通じてビルドされます。
そのため、直接起動するイメージの登録と、ビルドで使う基底イメージのキャッシュを区別する必要があります。
前回追加した事前検査には、この区別が不足していました。
`No such image` を理由に実機確認へ進めなかった直接原因は特定できました。

キャッシュの記録だけでは、現在の成果物を使うビルドの成功までは確認できません。
今回の調査では、実際のイメージビルドも、イメージ配布元への接続を伴う取得も実施していません。
外部通信なしで必ずビルドできることや、追加取得が不要であることは未実証です。

事前検査でも、すべての確認を削除して無条件に実機起動へ進める方法は候補にしていません。

後続の実機操作は、今回の原因調査の許可に含めていません。
強制削除や権限変更も候補の範囲外です。
