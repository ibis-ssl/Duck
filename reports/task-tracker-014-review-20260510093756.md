## 指摘事項

- blocking normal-path problems:
  1. `TrackerCoordinator.RequestProfileSwitch(...)` の duplicate 判定が `ProfileName` と UDP publish 先の一部しか見ておらず、同一 profile 上で runtime override だけを変える request を no-op 扱いで握りつぶします。`TrackerProfileRequestService` と `TrackerConfigurationResolver.Resolve(...)` は `RobotTracker` / `BallTracker` / `KickDetector` の override を request 経路に載せる実装になっているのに、`AreResolvedOptionsEquivalent(...)` はそれらを比較していません。このため「同じ profile で tuning だけ変える」「同じ publish 先のまま tracker parameter だけ apply する」という正常系が engine まで到達しません。`Tracker/Tracker.Server/Tracking/TrackerCoordinator.cs:69-74`, `Tracker/Tracker.Server/Tracking/TrackerCoordinator.cs:237-245`, `Tracker/Tracker.Server/Tracking/TrackerProfileRequestService.cs:10-19`, `Tracker/Tracker.Core/Design/tracker-architecture-plan.md:555-577`
- user-confirmation-required gaps:
  1. 実ランタイムでは `TrackerProfileRequestService` が DI 登録されただけで、現状それを呼ぶ server 側の入口がありません。workspace 全体での参照は `Program.cs` と unit test のみで、現行 `Home.razor` も `VisionPacketStore` しか inject していません。`TRACKER-014` の exit criteria を「将来 UI から使える内部 request 経路を先に作る」までに限定するなら許容できますが、`tasks-status.md` の文言どおり「server から engine へ request が流れる実行可能経路」を今回で完了させる解釈なら未達です。これは `TRACKER-017` 以降へまたがる可能性があるため、task 完了判定の前にスコープ確認が必要です。`Tracker/Tracker.Server/Program.cs:26-29`, `Tracker/Tracker.Server/Components/Pages/Home.razor:1-89`, `Tracker/Tracker.Core/Design/tasks-status.md:7-15`, `Tracker/Tracker.Core/Design/tasks-status.md:34-37`
- non-blocking held concerns: なし。
- 指摘要約または「指摘なし」: 指摘あり。control-only drain、snapshot clear、publisher port 切替自体は `TrackerCoordinatorTests` / `TrackerProfileRequestServiceTests` の追加ケースと対象 test 実行で確認できた一方、runtime override を含む reconfigure request の duplicate 判定が設計どおりの `desired target snapshot` 比較になっておらず、同一 profile での override apply 正常系を壊している。

## 結果

- 結果: `fail`。対象 test 10 件は通過したが、`TrackerCoordinator` の request 同値判定が runtime override 差分を無視しており、設計上同じ経路で扱うはずの reconfigure 正常系を server から engine へ流せない。加えて、実ランタイムでその request を発行する入口が今回の差分だけでは露出していないため、`TRACKER-014` を完了扱いにする前に scope 解釈の確認が必要。

## リスク

- 未解決のリスクまたは後続対応: duplicate 判定の blocker を解消しないまま進めると、将来 `TRACKER-017` 以降で同一 profile に対する tuning apply UI を追加しても request が coordinator で黙って破棄される。加えて、実際の request 発火入口をどの task で持つかを曖昧にしたまま進めると、`TRACKER-014` と `TRACKER-017` の完了条件が重複して進捗判定がぶれる。
