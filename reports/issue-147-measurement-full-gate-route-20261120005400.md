先行PR148の候補 `7123076d3a1ada9da7db5012e65f48099ed2c33f` で局所と通常レビューを終え、標準の全体.NET試験を実行した。ローカルのコマンドが実行可能であることと、リポジトリの全体ゲートを成立させる環境があることを区別する。

| 実行環境 | 結果 |
| --- | --- |
| FA780 Windows、標準Debug | 終了値1。1,527成功、8失敗、2スキップ。失敗8件は基準mainと同じ `MatchLinuxBindPermissionsTests` の非Linux動的スキップがランナーで失敗として数えられたもの。計測ツール20件は成功。 |
| 使い捨てLinux、既存キャッシュのみ | 復元で終了値1、試験未実行、TRXなし。宣言済みAspireのLinux用実行物2件が不足。 |
| 使い捨てLinux、上記2件の公式取得後 | 終了値1。1,523成功、10失敗、4スキップ。計測ツール20件は成功。失敗9件はモデル構築時のDocker CLI起動、1件は内部ブリッジからのマルチキャスト参加。 |

Linuxの実行には公式SDK10.0.404を使用し、`sha256:a82c44c2efe00953d66a37e90d307c4cfbd1e974b16e3b2a2fc665331946c9af` に固定した。候補と3サブモジュールの固定内容をアーカイブのSHAで照合し、Ubuntu 24.04の非root `1654:1654` で実行した。書き込み先を専用領域へ分け、ホストの既存NuGetキャッシュは読み取り専用で参照した。アプリの依存宣言・版、認証、永続設定は変更していない。

取得したのは、既存Aspire13.5.4のOS別実行物 `Aspire.Dashboard.Sdk.linux-x64` と `Aspire.Hosting.Orchestration.linux-x64` の13.5.4だけ。公式NuGetのURL、nuspec、バイト数とSHAは作業木外の取得明細に保存した。今回のコンテナと専用ネットワークは回収し、既存のコンテナとネットワークは変更していない。

9件は試験自体でコンテナを起動しないが、AppHost初期化が `docker context show` と `docker --context … info --format '{{.ID}}'` によりEngineの識別情報を読む。CLIだけを加えても応答するEngineが必要である。ホストのDockerソケットを検証コンテナへ渡す構成は採用しない。残る参加エラーは内部ネットワークの経路不足が有力だが、数値エラーコードを採取しておらず原因確定とはしない。

## 正式な全体ゲートの選択

局所用の `local_execution_available` の証拠は維持する。一方、許可した隔離構成には標準全体試験が必要とするEngineと通信環境が揃わないため、**全体ゲート工程は `remote_ci_only` として既存のGitHub Linux `pull_request` CIを使う**。ローカルの失敗を成功へ読み替えず、除外フィルターや試験・製品の無関係な修正で成功を作らない。切り替えは明示し、性能測定の実行先はFA780のまま変えない。

この報告を含む候補を、本人が許可した非mainブランチへ通常pushし、同じheadのCIで標準試験を確認する。CIが成立するまでは全体ゲート完了・独立最終レビューの準備完了とは扱わない。通常レビューは収束しており、ここからの差分は報告だけである。

CI確認後に独立最終レビューを実行する。報告の確定後は実装対象と報告だけのコミットを区別し、最終公開headのCIも確認する。現時点で既存文書の全体検査の指摘は課題144へ保留し、新規文書違反がないこととは区別する。UDPでの性能、多カメラ、追跡精度と他実装の同条件比較は未検証。
