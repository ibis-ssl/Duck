## 指摘事項

- 指摘要約または「指摘なし」:
  - [P2] `ComparisonSnapshotIndex.FindNearest` が同一 timestamp の candidate 群から 1 件だけを前後比較するため、既存の nearest comparison 選択順が変わる可能性がある。旧実装は `snapshots` を `TrackedFrameTimestampNs`、`ReceivedAt` で整列した後、`OrderBy(delta).ThenBy(timestamp).First()` で選んでいたため、同じ nearest timestamp に複数 candidate がある場合は整列順の先頭、つまり同一 timestamp 内では最も早い `ReceivedAt` が選ばれる。新実装は `FindInsertionIndex` の直前 candidate だけを見るため、target より小さい同一 timestamp 群では末尾、つまり遅い `ReceivedAt` 側を選ぶ。All filter で複数 external source が同一 tracker timestamp を持つ capture や、同一 source label に同 timestamp の複数 record がある capture で、表示される nearest source / frame / ball・robot count がTRACKER-055前と変わりうる。既存の source option / nearest comparison / All filter 挙動維持がレビュー条件に含まれているため、timestamp重複時も旧実装と同じ tie-break を保つよう、binary search後に同一 timestamp 範囲の先頭候補を選ぶなどの修正が必要。参照: `Tracker/Tracker.Server/Tracking/TrackerDiagnosticsComparisonViewStateReader.cs:595`、`Tracker/Tracker.Server/Tracking/TrackerDiagnosticsComparisonViewStateReader.cs:606`、`Tracker/Tracker.Server/Tracking/TrackerDiagnosticsComparisonViewStateReader.cs:636`

## 結果

- 結果: blocking finding あり。focused test は 31 passed、`git diff --check` は passed。sidecar index cache は同一 file state の連続 `Load` で再構築しない経路になっており、cache key も diagnostics log / metadata / sidecar の path・存在・mtime・length を含む。通常 Play は実 timestamp delta のまま、Fast Forward だけ speed multiplier を使う実装になっている。ただし nearest candidate の tie-break regression があるため、TRACKER-055完了扱いには修正と再レビューが必要。

## リスク

- 未解決のリスクまたは後続対応:
  - metadata file state 変更による cache invalidation は実装で満たしているが、focused test は sidecar変更のみを直接検証している。修正時に metadata / diagnostics log の file state 変更でも cache key が変わることを追加で押さえると、今回の設計意図をより明確に固定できる。
  - 初回 index build は sidecar size に比例する。これは今回の許容範囲だが、同時初回アクセスでは同じ key の index build が重複しうるため、巨大 session を複数ユーザーで同時に開く運用では一時的な負荷が残る。
