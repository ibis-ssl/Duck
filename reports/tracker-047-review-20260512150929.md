## 指摘事項

- Blocking normal-path problems:
  - High: `TrackerSnapshotReplayReader` の nearest timestamp summary が、diagnostics log 先頭の wall-clock `receivedAt` を 1 分内 ns に丸めた値と、snapshot 側 `TrackedFrame.timestamp` 由来の `TrackedFrameTimestampNs` を比較している。該当箇所は `Tracker/Tracker.Server/Tracking/TrackerSnapshotReplayReader.cs:111` と `Tracker/Tracker.Server/Tracking/TrackerSnapshotReplayReader.cs:188`。既存 diagnostics log は `Tracker/Tracker.Server/Tracking/TrackerCoordinator/Diagnostics.cs:42` で `receivedAt` を行頭 timestamp に出しており、ibis committed frame の `TrackerFrame.DataTimestampNs` は `Tracker/Tracker.Core/Model/TrackerFrame.cs:14`、official packet 側の `TrackedFrame.timestamp` は `Tracker/Tracker.Core/Proto/TrackerPacketGenerator.cs:43` で別に扱われる。設計は `Tracker/Tracker.Core/Design/tracker-server-cli-ui-detail-design.md:77` と `Tracker/Tracker.Core/Design/tracker-architecture-plan.md:143` で ibis `TrackerFrame.data_timestamp_ns` と snapshot `TrackedFrame.timestamp` の nearest/latest-before 比較を求めているため、実運用の replay / diagnostics / playback では近傍 snapshot を誤選択する。テストは wall-clock の秒部分を snapshot timestamp に合わせているため、この不整合を検出できていない。
  - Medium: 今回追加された public replay DTO record の positional properties に XML documentation がない。該当箇所は `Tracker/Tracker.Server/Tracking/TrackerSnapshotReplayReader.cs:197`、`Tracker/Tracker.Server/Tracking/TrackerSnapshotReplayReader.cs:207`、`Tracker/Tracker.Server/Tracking/TrackerSnapshotReplayReader.cs:222`、`Tracker/Tracker.Server/Tracking/TrackerSnapshotReplayReader.cs:232`、`Tracker/Tracker.Server/Tracking/TrackerSnapshotReplayReader.cs:240`。`source-documentation-policy.md` は public / internal API surface と DTO property の XML documentation 不足を blocking として扱うため、type summary だけでは `DiagnosticsLogPath` の null 意味、`MatchingRule` の値、`RawPayloadRestored` の意味などの public contract が記録されていない。
- User-confirmation-required capability gaps:
  - なし。
- Non-blocking concerns / held concerns:
  - speculative hardening として指定された socket abstraction、DI startup test、invalid raw payload direct append handling は、今回確認した範囲では通常経路を追加で壊していないため held concern のまま扱う。

## リスク

- timestamp finding を直さないまま `TRACKER-048` で UI / replay 出力へ接続すると、表示上は nearest summary が存在しても、実際には diagnostics committed frame と無関係な tracker snapshot を比較対象として出す可能性がある。
- XML documentation finding を直さないまま進めると、今回追加した replay DTO の public contract が次タスクの diagnostics / playback 接続時に曖昧になり、source shape policy の review gate を再度失敗する可能性が高い。
- 既存検証は green だが、timestamp の実時間軸不一致を固定するテストがないため、修正時は wall-clock receivedAt と data timestamp を意図的にずらした regression test が必要。
