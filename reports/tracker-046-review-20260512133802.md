## 指摘事項

- Blocking normal-path problems:
  - [High] `Program.cs:59-64` は `TrackerPublisherOptions.Port` だけで `UdpTrackerReceiver<TrackerPacketAdapter>` を生成し、`UdpTrackerReceiver.cs:23-37` も `IPAddress.Any` へ bind するだけで configured `MulticastAddress` を受け取らず `JoinMulticastGroup` もしない。設計上の official tracker packet は既定 `224.5.23.2:10010`、現 `sim` profile は `224.5.23.2:11010` の multicast 配信だが、`TrackerRuntimeRegistrationTddTests.cs:165-170` は loopback unicast 送信だけを検証している。このままだと実運用の official multicast tracker packet が live receiver に届かず、CaptureOn 中の snapshot sidecar へ保存されない可能性が高い。unicast-only 傍受を今回の意図として親が明示確認するのでなければ、runtime 正常系 blocker として multicast receive contract / 実装を追加すべき。
- ユーザー確認が必要な capability gap:
  - [Medium] `Program.cs:59-68` は receiver と HostedService を無条件登録し、`TrackerConnectionLibReceiverHostedService.cs:31-38` は起動時に必ず `receiver.Start()` する。一方で既存設定には `TrackerOptions.Enabled` / `PublishUdp` があり、`TrackerOptions.cs:10-18` は tracker pipeline と UDP publish の有効化を表すが、この新 receiver はどちらも見ていない。`PublishUdp=false` や `Tracker.Enabled=false` でも port bind と受信処理が始まるため、「危険なデフォルトで勝手にネットワーク受信を始めない」条件に対して、常時受信を仕様とするのか、既存 gate に連動させるのか、または専用 receive/capture option を追加するのか親判断が必要。
- Non-blocking concerns:
  - [Low] `RuntimeStartup_RegistersLiveTrackerReceiverRecorderAndHostedConnection` は `TrackerRuntimeRegistrationTddTests.cs:37-57` で assembly 内の `IHostedService` 型と constructor 形だけを見ており、`Program.cs:67-68` の DI / `AddHostedService` 登録そのものは検証していない。現実装には登録があるため今回の blocker ではないが、今後 `AddHostedService<TrackerConnectionLibReceiverHostedService>()` が消えてもこの test は通る。
  - [Info] `UdpTrackerReceiver.cs:107-116` は handler 例外を receiver loop から隔離して `HandlerErrorCount` へ集計するため、CaptureOff 競合で HostedService が止まる問題は normal path 上は抑えられている。ただし exception detail は保持しないため、継続的な保存失敗の診断性は後続 hardening 候補。

## 結果

- gpt-5.5 high 指定の専用レビューとして、`TRACKER-046` の runtime 起動登録実装・テスト・tracking 差分をレビューした。
- `TrackerConnectionLibReceiverHostedService` により `UdpTrackerReceiver<TrackerPacketAdapter>`、`MultiTrackerManager<TrackerPacketAdapter>`、`TrackerConnectionLibSnapshotRecorder` が constructor で常駐接続され、`Program.cs` でも DI / HostedService 登録されていることは確認した。
- `TrackerWrapperPacketDeserializer` は uuid / sourceName 空の protobuf packet を落とさず、`MultiTrackerManager` は own / external / unknown の `SourceRole` / `SourceLabel` を保存経路へ渡せることを確認した。
- `UdpTrackerReceiver` は handler 例外を receiver loop から隔離しており、writer 例外で receive loop / HostedService を止めない実装になっていることを確認した。
- diagnostics / replay / playback UI 実装と PR ready 化は tracking 上も今回対象外として切られていることを確認した。
- 関連 focused test 結果: 38 passed / 0 failed / 0 skipped。
- full `Tracker.Tests` 結果: 183 passed / 0 failed / 0 skipped。
- test 実行時に NuGet vulnerability data の read-only cache warning が出たが、test は成功した。

## リスク

- official tracker packet の実運用 source を multicast とみなすなら、現 receiver は multicast group に参加していないため `TRACKER-046` の normal path は未充足。
- receiver 起動条件は未確定。常時受信を許容するか、`Tracker.Enabled` / `PublishUdp` / 新 option のいずれで制御するか親判断が必要。
- runtime DI 登録を実際の `Program.cs` 構成として守る test は不足している。
- diagnostics / replay / playback UI は後続範囲として残っており、このレビューでは実装完了とは扱っていない。
