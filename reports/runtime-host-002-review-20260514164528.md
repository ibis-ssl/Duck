## 指摘事項

### Blocking normal-path problems

1. `Tracker/Tracker.Tests/RuntimeHostDependencyBoundaryContractTests.cs:28` から `Tracker/Tracker.Tests/RuntimeHostDependencyBoundaryContractTests.cs:41` の project reference 判定は、`ProjectReference Include` の文字列を `/` へ置換しただけで、`reference.EndsWith("Tracker/Tracker.Server/Tracker.Server.csproj")` のように比較している。実際の sibling project reference は `Tracker/Tracker.Server/Tracker.Server.csproj:11` のように `..\Tracker.Core\Tracker.Core.csproj` 形式で書かれるのが既存 pattern であり、将来 `Tracker.RuntimeHost` から `..\Tracker.Server\Tracker.Server.csproj` または `..\Tracker.DebugHost\Tracker.DebugHost.csproj` を参照しても、normalized string は `../Tracker.Server/Tracker.Server.csproj` となって forbidden suffix に一致しない。このため、RUNTIME-HOST-002 の exit criteria である「RuntimeHost が DebugHost / Server / diagnostics replay UI project を参照しないこと」を false negative で取り逃がす。

### ユーザー確認が必要な capability gap

- なし。

### Non-blocking concern / hold

- `Tracker/Tracker.Tests/RuntimeHostDependencyBoundaryContractTests.cs:95` から `Tracker/Tracker.Tests/RuntimeHostDependencyBoundaryContractTests.cs:104` の DebugHost loop ownership marker は、`AddHostedService<VisionReceiverService>` など現在の tracker operation loop に近い実装名を直接禁止している。現状の Red contract としては妥当だが、後続で raw-only / read-side 用 receiver が同名または hosted service 形状で残る場合に false positive になる余地がある。これは後続実装時に service 名や marker を boundary の本質、つまり `TrackerCoordinator.ProcessPacket`、`ITrackerEngine`、`ITrackerPacketPublisher`、`TrackerPacketGenerator` の所有禁止へ寄せれば回避できるため、現時点では hold とする。
