## 指摘事項

- 指摘要約または「指摘なし」:
- Blocking normal-path problem:
- `Tracker/Tracker.Server/Components/Pages/DiagnosticsPlaybackState.cs:57`-`60` と `Tracker/Tracker.Server/Components/Pages/Diagnostics.razor.cs:651`-`658`: Fast Forward が unified replay timeline の tick を 1 tick ずつ辿らず、`speedMultiplier / 4` 分だけ index を進めたうえで、さらに `GetInterval(...)` 側でも timestamp delta を speed で割っている。設計 report と design doc は「Fast Forward の倍率は timeline tick 数ではなく capture-time delta の短縮として扱う」「Play / Fast Forward / scrub は unified replay timeline index を使う」としており、fast tracker tick 0/20/40/60/80/100ms の normal path では Fast Forward 16x が 0ms から 80ms へ飛ぶため、20/40/60ms の selected replay timeline tick、Field source、overlay、comparison が再生中に選択されない。`Tracker/Tracker.Tests/DiagnosticsPlaybackStateTests.cs:21`-`34` は旧 entry skip contract をそのまま固定しており、TRACKER-059 の Fast Forward acceptance を逆向きに通している。修正が必要。
- User-confirmation-required capability gap:
- `Tracker/Tracker.Server/Tracking/TrackerSnapshotAlignmentLogWriter.cs:172`-`185`: tracker snapshot tick では append された 1 source の record だけを同じ `ReplayTimelineIndex` に保存している。ER-FORCE だけを Field source / comparison で見る normal path は通るが、同一 capture に複数 tracker source があり、ある source の fast tick 上で別 source を selector から選ぶ場合、selected replay timeline tick の latest-before alignment は保存済み record から解決できない。現状は `TrackerDiagnosticsComparisonViewStateReader` が diagnostics line / nearest timestamp fallback へ落ちるため、`TrackedFrame.timestamp` 非重複 source では意図しない frame を出す可能性がある。複数外部 source を同一 tick 上で latest-before hold することまで TRACKER-059 の normal path に含めるか、ユーザー確認が必要。
- Non-blocking held concern:
