# 課題81: 標準ネットワーク識別の検査を修正

## 1. 変更前に何が困っていたか

公開版5223f1c0の標準`bridge`初回で、所有元と依存側は起動し、所有・固定イメージの照合を通過した。その後、検証器がネットワーク情報を拒否し、再作成以降へ進めなかった。元の検査情報は保存しておらず、この回の拒否条件は未確定である。

同じ通常担当は別途、合法な完全ネットワークID指定を名前との文字列比較で拒否する `I81-07E-NR001`、P2を確認した。DCPがIDを作成引数へ渡す場合に対応できず、所有元と依存側の同じネットワークを別の表現として拒否する実装だった。

## 2. 今回、何ができるようになるか

単一の接続情報に含まれる検証済みの名前と完全IDへ解決し、同じ実ネットワークかを比較する。`mode`は`default`、その接続の名前、またはその完全IDだけを受理する。生の`mode`文字列同士の一致を必須にしない。異なるID・不明値・追加接続・禁止された方式を拒否する条件は保持する。

## 3. どのように動くかの要点

実測側と単体試験は同じ検証処理を呼ぶ。既存の所有とイメージの照合後、検証前に対象2資源の`mode`、接続件数、先頭最大2件の名前・ID・IPv4だけを長さ上限付きで記録する。環境変数・引数・ラベル・検査情報全体は出力しない。不正な入力でも限定記録が元の検証例外を隠さないことを確認する。新しいDocker操作や設定変更は追加しない。

## 4. 今回含まないこと・後続に残すこと

標準`bridge`初回の試験全体は不合格のまま、依存側起動成功と区別する。共有方式の過去3回も変更しない。通常`base`のCrane・既定CM4の所有移行、固定`127.0.0.1`を含む通信互換性、再設定と通信再接続、全体独立最終確認は残る。今回の表現修正を通常構成全体や共有方式の合格へ流用しない。

## 5. 検証できたこと・未検証のこと

共有処理の先行試験では合法ID指定2件と限定記録1件が失敗し、不正入力の元例外保持1件は成功した。修正後は対象18件と関連7試験群159件が成功し、実測用2件は未実行だった。対象18件は159件に含まれる。今回の試験実行でAppHostと審判受信側を含む依存ビルドも成功した。製品側の実装ファイルとプロジェクトは不変で、個別ビルドの直前の成功証拠と区別して記録する。必要文書検査の入力指紋と終了値は別の記録に保存する。同担当の解消確認と修正後の新実測は未実施である。

標準`bridge`初回は約11秒で停止・消失を確認し、元プロセスと関連試験プロセスの終了、後続の所有ラベル付き資源残存0を照合済みである。再作成・接続の検証は到達していない。

## 6. 判断してほしい操作と、その影響

新たな判断依頼はない。既存許可内で通常反映と同担当の解消確認を行い、各回2資源・最大4世代・60秒、固定キャッシュ・読み取り専用配布物・127.0.0.1の動的`TCP`だけで再試験する。前回の終了を確認し、今回所有する資源だけを片付けて残存を照合する。追加取得・UDP追加・Docker Desktop・`Engine`・`context`の設定変更は行わず、統合や完了認定は求めない。
