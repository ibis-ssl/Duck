## 指摘事項

- 指摘要約または「指摘なし」: 4件（blocking 1件、user confirmation が必要な capability gap 2件、record only の non-blocking concern 1件）
- Blocking: `Tracker/Tracker.Server/README.md:80` と `Tracker/Tracker.Server/README.md:84` は `http://localhost:5289` への `POST` で `202 Accepted` が返る前提になっているが、実装は `Tracker/Tracker.Server/Program.cs:41` で `UseHttpsRedirection()` を有効化しており、既定 launch profile も `Tracker/Tracker.Server/Properties/launchSettings.json:17` で `https://localhost:7042;http://localhost:5289` を同時公開している。そのため README の `curl` 例は通常系でそのまま `202` にならず redirect を踏む。README の公開手順として壊れているので、このまま release には出せない。
- User confirmation が必要な capability gap: `Tracker/Tracker.Server/Components/Vision/TrackedDetailsPanel.razor:25`-`30` は `Publish OK` / `Publish Fail` を publish 成否として表示しているが、実装では `Tracker/Tracker.Server/Tracking/UdpTrackerPacketPublisher.cs:37`-`40` が `PublishUdp=false` なら無送信で即 return し、その直後に `Tracker/Tracker.Server/Tracking/TrackerCoordinator.cs:122`-`126` が例外なしとして `RecordPublishSuccess()` を増やす。README `Tracker/Tracker.Server/README.md:9` と `Tracker/Tracker.Server/README.md:108` の説明と組み合わせると、UDP 無効時でも UI 上は publish 成功が積み上がるため、viewer から送信停止を正しく確認できない。
- User confirmation が必要な capability gap: `Tracker/Tracker.Server/Program.cs:48`-`54` の API は存在しない profile 名でも事前検証せず `Tracker/Tracker.Server/Tracking/TrackerProfileRequestService.cs:15` から `Tracker/Tracker.Server/Tracking/TrackerConfigurationResolver.cs:17`-`20` の例外へ落ちる。`Tracker/Tracker.Tests/TrackerProfileRequestServiceTests.cs:67`-`88` でも unknown profile が throw する契約になっている。README `Tracker/Tracker.Server/README.md:83`-`85` は failure 自体には触れているが、user-facing API としては 4xx ではなく 500 系挙動になる点をどう扱うかは確認が必要。
- Non-blocking concern: `Tracker/Tracker.Server/README.md:108` の `PublishUdp=false` 説明は通常系としては正しいが、実装では `Tracker/Tracker.Server/Tracking/UdpTrackerPacketPublisher.cs:19`-`30` が `PublishUdp` の真偽に関係なく送信先 address を検証し、`Tracker/Tracker.Server/Tracking/TrackerCoordinator.cs:50` と `Tracker/Tracker.Server/Tracking/TrackerCoordinator.cs:108` でも常に publisher 設定を適用する。したがって UDP 送信を止めても publish 設定は syntactically valid である必要がある。既定設定のままなら回避できるため、記録のみとする。

## 結果

- 結果: blocking finding が 1 件あるため review は pass 扱いにできない。`Enabled` の説明と profile switch 後の clear/repaint 挙動は概ね整合している一方、API 利用手順の HTTP/`202` 記述は修正が必要で、`PublishUdp=false` 時の UI publish 表示と invalid profile API 応答は scope 拡張有無の確認が必要。

## リスク

- 未解決のリスクまたは後続対応: README 修正時は `curl` 例を HTTPS 側へ寄せるか redirect 前提を明示したうえで、invalid profile 名の扱いを docs だけで済ませるのか、API の validation / status code まで広げるのかを決める必要がある。`PublishUdp=false` の注意は実害化していないが、viewer-only 運用手順を厚くする場合は補足候補になる。
