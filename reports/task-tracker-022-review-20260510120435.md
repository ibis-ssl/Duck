## 指摘事項

- 指摘要約または「指摘なし」: [blocking] `Tracker/Tracker.Server/Program.cs:14-22` は startup 時の receiver 設定だけを `Tracker:ActiveProfileName` から解決していますが、同じ起動文脈の active profile 表示 source of truth は更新していません。`TrackedSnapshotStore` は依然として `default` で初期化され (`Tracker/Tracker.Server/Tracking/TrackedSnapshotStore.cs:10`)、UI 側も `snapshot.ActiveProfileName` をそのまま優先するため (`Tracker/Tracker.Server/Components/Vision/TrackerProfileControlViewState.cs:16-18`)、`README.md:125` と `README.md:255-263` や `tracker-architecture-plan.md:340-342,563-566` が案内する「非 default の起動 profile」を使うと、実際の tracker / receiver は `sim` や `fast` で起動しているのに、画面上の active profile は最初の frame または手動 switch まで `default` のまま表示されます。TRACKER-022 は startup 初期化と receiver 追従を売りにしているため、この観測可能な不一致は正常系の確認を壊す blocking 問題です。 [record-only] `Tracker/Tracker.Tests/VisionReceiverConfigurationResolverTests.cs:115-150` は startup 時の receiver store 解決までは固定していますが、今回の不一致を起こしている `TrackedSnapshotStore` / profile control 側まで通した検証はありません。今回の regression が test で捕まらなかった理由として記録し、修正時に startup active profile 表示まで含めた test を足すべきです。 user confirmation が必要な capability gap は今回は見当たりません

## 結果

- 結果: review fail。blocking 1 件、user confirmation が必要な capability gap 0 件、record-only concern 1 件。`Tracker:ActiveProfileName` を非 default で起動したときの active profile 初期表示と実際の receiver / tracker 起動状態を一致させる修正が入るまで tracking を進めるべきではない

## リスク

- 未解決のリスクまたは後続対応: このまま進めると non-default startup profile 利用時に「receiver は切り替わっているが UI は default を示す」状態が残り、TRACKER-022 で追加した receiver profile 追従の切り分けが難しくなる。後続対応では `TrackedSnapshotStore` の初期 active profile を startup 設定とそろえること、およびその表示まで含む test を追加して regression を塞ぐこと
