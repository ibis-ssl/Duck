# #114 Positive readiness for match participants

Parent: #43. This follow-up implements the existing match-readiness contract for Sumatra (`tigers-blue`), AutoRef (`autoref-tigers`), and `ssl-log-recorder`.

The match controller must receive fresh, positive, resource-specific readiness evidence tied to the resource instance, full container ID, and run ID. Running alone, or null/unknown health, is not readiness. The current fail-closed predicate is in PR #113; this issue establishes the missing producer-side signals and their real-container verification.

The accepted design at `aspire-simulation-test-environment.md` lines 42 and 237 requires checking participant readiness and implementing required receive/decode diagnostics in the corresponding container when no verification endpoint exists. Existing pinned images/launch arguments and bridge/ports remain the baseline.

Completion requires focused tests plus positive and negative checks against the actual target containers on the actual configured network. Mock-only notifications or synthetic evidence cannot establish completion. This work covers per-service readiness only; it does not run or replace #50's broader live match/ASPIRE-MATCH packet acceptance.

## Participant evidence and permitted transports

The match path has two evidence phases. Before start, require the accepted API/referee/vision prerequisites and only those participant functions that have an observable, resource-specific pre-start signal. After start, separately require evidence of the behavior that can only occur during play, such as AI motion, AutoRef proposals, and match acceptance. A post-start behavior must not be a pre-start prerequisite when doing so would prevent the controller from producing it; a startup marker must not substitute for missing post-start behavior. Apply bounded deadlines and persist partial evidence when either phase fails.

Evidence may come from a participant's native output when it demonstrates the required function, or from an observer that decodes that output. Describe exactly what the observation proves; observer-side decoding is not a claim that the target internally decoded its input. Every observation must be bound to the current registered resource, full container ID, run ID, and generation. Verify ownership and generation before and after collection; reject changes and invalidate retained evidence on replacement. Preserve source event times and new activity: rereading old evidence must not renew freshness. Missing identity, unavailable diagnostics, unknown age, stale activity, or failed collection leaves the participant unready with a specific reason and partial evidence.

Existing endpoints, Docker timestamped logs addressed to the verified full container ID, and output records produced by that container are permitted evidence transports. Preserve Docker event timestamps rather than assigning collection time to retained logs. Startup markers establish startup only, not continuing activity. A behavior that can occur only after the referee start command is evidence for the post-start phase, not the pre-start gate.

- **Sumatra (`tigers-blue`):** Fresh native frame-processing evidence from its verified full-ID logs can establish pre-start vision-processing readiness; tracker packets on `224.5.23.2:11010` may establish world-processing preparation if newly emitted packets are decoded and the sender address is bound to the current container and run. The existing monitor's source-name check alone is insufficient. These signals do not establish referee processing or in-game AI motion; verify AI motion in the post-start phase.
- **AutoRef (`autoref-tigers`):** Startup, ACTIVE mode, registration, connection presence, or another observer's packet reception does not establish functional readiness. A fresh AutoRef-originated proposal or other native processing result during the real match can establish post-start behavior when its source is bound to the current resource generation. No pre-start functional signal or reliable current-container mapping is established yet; keep that evidence false/partial until verified rather than treating a startup marker as Ready.
- **Recorder (`ssl-log-recorder`):** Require fresh complete SSL-log records with decoded payloads for Referee, SSL-Vision, and vision-tracker inputs, attributed to the current recorder container generation and run. File existence, size, modification time, or byte growth alone is insufficient. The version-1 record reader must validate the header, complete framing, message type, payload Protobuf, and receiver timestamp. A complete record prefix from a live gzip stream may prove recording progress without a final gzip footer; decompressed EOF is not a gzip-integrity claim. The recorder's file does not contain sender endpoints, so do not claim per-sender identity from its records. The implementation uses one cancellable sequential reader per current archive generation and consumes appended records incrementally; it has no archive-lifetime byte cap. The existing 16 MiB per-record bound remains. The preserved 420-second archive was 9.6 MiB compressed and 59 MiB decoded; its offline parse validates framing and payload protobufs, but does not establish live readiness or sender identity.

HTTP endpoints, Docker HEALTHCHECK, and the current two-minute log lifetime are implementation mechanisms, not readiness evidence. They do not replace resource-specific positive activity, ownership and generation checks, freshness, fail-closed behavior, bounded phase deadlines, or real-container/network verification. Do not report the match-start gate as passed until the required pre-start evidence passes. Do not report end-to-end match acceptance as passed until its post-start evidence also passes; preserve a partial result when either phase times out or fails. Document and verify the freshness bound selected for each signal.
