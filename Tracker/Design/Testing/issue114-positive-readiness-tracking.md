# #114 Positive readiness for match participants

Parent: #43. This follow-up implements the existing match-readiness contract for Sumatra (`tigers-blue`), AutoRef (`autoref-tigers`), and `ssl-log-recorder`.

The match controller must receive fresh, positive, resource-specific readiness evidence tied to the resource instance, full container ID, and run ID. Running alone, or null/unknown health, is not readiness. The current fail-closed predicate is in PR #113; this issue establishes the missing producer-side signals and their real-container verification.

The accepted design at `aspire-simulation-test-environment.md` lines 42 and 237 requires checking participant readiness and implementing required receive/decode diagnostics in the corresponding container when no verification endpoint exists. Existing pinned images/launch arguments and bridge/ports remain the baseline.

Completion requires focused tests plus positive and negative checks against the actual target containers on the actual configured network. Mock-only notifications or synthetic evidence cannot establish completion. This work covers per-service readiness only; it does not run or replace #50's broader live match/ASPIRE-MATCH packet acceptance.

## Participant evidence and permitted transports

The following rules clarify evidence transports and supplemental observations without changing the accepted target-side receive/decode requirements. Every participant must retain fresh evidence of its own required input receive/decode activity; output observation alone cannot satisfy this requirement. Every observation must be bound to the current registered resource, full container ID, and run ID. Verify ownership and generation before and after collection; reject changes and invalidate retained evidence on replacement. Preserve event times and new activity evidence: rereading old evidence must not renew freshness. Missing identity, unavailable diagnostics, unknown age, stale activity, or failed collection leaves the participant unready with a specific reason and partial evidence.

Existing endpoints, Docker timestamped logs addressed to the verified full container ID, and output records produced by that container are permitted evidence transports. A transport carrying only independently decoded output cannot substitute for target-side diagnostics. Preserve Docker event timestamps rather than assigning collection time to retained logs. Startup markers establish startup only, not continuing activity.

- **Sumatra (`tigers-blue`):** The existing `TrackerPacketReadinessMonitor` may be reused to observe fresh, decoded, newly emitted tracker packets on `224.5.23.2:11010` from within the configured container network, only if the observed sender address can be bound to the inspected current container, full container ID, and run ID. Retain and revalidate that network attribution; the monitor's current source-name check alone is insufficient. This is supplemental target-produced output evidence only and does not verify or satisfy Sumatra's target-side input receive/decode requirement. Substituting this output for required target-side diagnostics is an unresolved design-owner decision; this document grants no such authorization.
- **AutoRef (`autoref-tigers`):** Require continuous evidence of AutoRef's own decoded inputs or processing of those inputs. Startup, ACTIVE mode, registration, connection presence, or another observer's packet reception is insufficient. Remain unready when suitable fresh processing evidence is unavailable.
- **Recorder (`ssl-log-recorder`):** Require new, complete live records with decodable payloads for the required recorder inputs, attributed to the current container and run. File existence, size, modification time, or byte growth alone is insufficient. Complete records decoded from an active gzip stream may support live recording evidence without a finalized gzip footer. These records do not replace the recorder's required target-side receive/decode diagnostics. Report final shutdown gzip integrity separately unless the applicable original acceptance criteria explicitly require it for readiness.

HTTP endpoints, Docker HEALTHCHECK, and the current two-minute log lifetime are implementation mechanisms. They do not replace the target-side receive/decode, identity, positive activity, freshness, fail-closed behavior, or real-container/network verification requirements. Document and verify the freshness bound selected for each signal.
