# 全体受入試験におけるチーム認識と審判状態の設計

## 目的

全体受入試験では、ロボット移動の開始前にGame ControllerとCraneのチーム名一致を確認する。この文書はその契約と今回の実装範囲を定める。移動中の審判状態監視は後続課題 #78 の子課題 #99 で扱う。

対象は試験用構成と受入検証である。本番の試合設定、Game Controller/AutoRef本体、追跡画面は変更しない。

## 実装範囲

今回の対象範囲は移動前のチーム認識とする。移動中の審判状態監視は子課題 #99 の設計契約に従う。

チーム名は設定値として管理し、Game Controllerの`Yellow`チーム状態とCraneの起動引数へ同じ値を伝える。色設定はチーム名と独立させる。

期待するチーム名が配信情報に現れ、CraneのROS設定値も一致するまで準備完了としない。準備未完了時はチーム名を設定し、配信状態の欠落や不一致を検出する。

専用失敗理由と詳細な履歴、試験専用AutoRef制御は後続課題 #78 の別範囲とし、この変更では着手しない。

## #99: 移動中の審判状態監視

黄色ロボットの移動確認中は映像検出の受信を続けると同時に、直前に確認した進行中の審判指令も監視する。受信した審判情報の指令番号が変わった時点で最新状態を確認する。指令が`NORMAL_START`または`FORCE_START`以外へ変わっていたら、審判状態の喪失として移動待ちを直ちに取り消す。指令番号が変わらない受信情報の全件保存は行わない。受信が途絶えた場合に失効とみなす新しい時間基準は設けず、既存の移動期限と外側からの中断を使う。

審判指令が維持されたまま移動が完了したら、状態監視を中断する。状態喪失、移動完了、外側で設けた受入期限のどの経路でも、相手側の待機処理を中断して終了を待ち、受入試験の後処理へ監視処理を残さない。

状態喪失の発生時は、後続課題 #100 で詳細な失敗理由と履歴形式を決められるよう、審判情報の最新一件を呼び出し元へ渡す。指令番号の全履歴や専用理由の文章はここでは定めない。AutoRefの設定や動作制御も対象外とする。

## #100: 状態喪失診断

移動中に進行状態の審判指令を失った場合、受入診断の`failure`には専用理由`REFEREE_STATE_LOSS`を記録し、`refereeStateLoss`には#99から渡された最新の状態記録を一度だけ含める。その記録の`Command`と`CommandCounter`は受信した実値を保持し、専用理由と同じ診断出力で確認できるようにする。移動完了時は状態喪失理由を出さず、移動期限切れは既存の`UDP_MOTION_FAILURE`で報告する。監視期限や停止動作は#99の契約を維持する。


## #101: 移動中の停止指令注入に対する回帰試験

自動回帰試験では、試験専用の `127.0.0.1` 上で `UDP` ソケットを空きポートに割り当て、審判 `protobuf` の `packet` を送信する。本番の `UdpRefereeCommandSource` で解析し、既存の受入試験と共用する記録用 `IRefereeCommandSource` 実装を通して履歴を保存する。移動処理が開始を通知した後に監視を始め、`NormalStart` から別の有効指令への変化を記録してから、移動中に新しい `Halt` を注入する。設定した `timeout` より前に移動を停止すること、最後の `command` と `counter` を含む `REFEREE_STATE_LOSS` 診断、指令履歴、ソケットの破棄を検証する。通常の移動完了は既存の移動監視試験で引き続き確認する。この回帰試験では Game Controller、AutoRef、Docker、`multicast`、Aspire 全体、映像、比較機能、100 mm 移動確認を起動せず、これらは個別に確認する証拠として扱う。

## 設定契約

| 設定 | 既定値 | 用途 |
| --- | --- | --- |
| `Testing:Crane:TeamName` | `crane` | AppHostが解決した値を実行ごとの設定ファイルに保存し、CraneとGame Controllerの黄色チーム名に使う。 |
| `Testing:Crane:TeamColor` | `YELLOW` | 黄チーム専用試験環境の`team_color`引数。`BLUE`は起動前に拒否する。 |
| `Testing:Crane:FixtureManifestPath` | 実行識別子から決める一時領域のJSON | AppHostが確定した`TeamName`、`TeamColor`、`StackId`だけを原子的に出力し、既存ファイルを上書きしない。 |

受入プロセスは同じ実行識別子と設定ファイルの場所を使う。欠落、破損、不正値、別の実行向けのファイルは失敗とし、設定ファイルに秘密情報を含めない。


`TeamName`は空でない`ASCII`英数字、`_`、`-`だけを許可する（`[A-Za-z0-9_-]+`）。それ以外はAppHost起動時に拒否し、シェル構文を起動引数へ渡さない。試験環境は黄チーム専用とし、`TeamColor`は`YELLOW`だけを受け付ける。`BLUE`はリソース作成前に拒否し、青チーム対応へ範囲を広げない。

## 値の伝播と準備完了

Craneには `team:=<TeamName>` を渡し、色は独立して `team_color:=<TeamColor>` とする。Game Controllerには公式の `UpdateTeamState` APIで`Yellow`のチーム名を設定する。

審判情報の`Yellow`側 `team_name` と、Craneの `/world_model_publisher` にあるROS設定値 `team_name` が同じ期待値であることを確認する。両方が一致するまで準備完了にしない。色の一致だけでチーム認識済みと判断しない。

## 再試行と配信欠落

起動時に送った設定要求も3回の共有上限に数える。後続の回復では残り枠だけを使い、正常復旧後も試行枠を補充しない。各回復は開始から最大10秒で、送信の制限時間と最終完了後1秒の確認猶予を残せない場合は新しい送信を始めない。

一度準備完了した後の黄チーム情報の欠落・不一致は回復状態として扱う。回復中は`/health/ready`を未準備に保ち、起動制御とDocker実行資源を稼働させる。黄チーム名が一致すれば準備状態を復旧する。最後の設定要求完了後は少なくとも1秒の配信確認猶予を置き、全体の回復上限10秒を超えた場合に限り起動制御を失敗終了して所有する実行資源の後始末をする。所有者不一致と期待プロセスの終了は回復待ちに入れず、即時失敗とする。

`Yellow`側の審判情報が欠落した場合は準備未完了とする。`Yellow`情報を含む有効な配信情報が再び届き、チーム名が期待値と一致すれば準備状態を回復する。チーム名を確認できない場合は準備完了にしない。

## 受入条件

| 受入項目 | 条件 |
| --- | --- |
| 入力検証 | 不正な `TeamName` はAppHost起動時に拒否し、安全な値だけをCraneとGame Controllerへ渡す。`TeamColor=BLUE`もリソース作成前に拒否する。 |
| チーム認識 | Craneの `team` と`team_color=YELLOW`を設定する。Game Controllerの`Yellow`側 `team_name` とCraneのROS設定値は同じ設定値に一致する。 |
| 再試行 | 起動時の設定要求は1秒間隔で最大3回。一度準備完了した後も不一致・欠落時は未準備を保って最大10秒回復を待ち、最終要求後に1秒以上の確認猶予を設ける。上限後は失敗終了して後始末する。 |
| 配信回復 | `Yellow`情報を欠く配信情報で準備未完了となり、有効な一致配信情報の再受信で回復する。回復中に `/health/ready` を成功扱いにしない。 |
| 移動前確認 | 全体受入試験はAppHostの実行ごとの設定ファイルを読み、識別子、チーム名、色を検証する。JSON、コマンドライン、環境変数の解決結果を使い、受入プロセス側で期待名を別設定しない。 |
| 移動と入力 | `Yellow`ロボットが100 mm以上移動し、Duckの追跡入力、比較用入力、専用環境の後始末を確認する。 |
| 状態監視 | 黄色ロボット移動中に審判指令を同時監視する。進行指令の喪失時は移動期限より前に停止し、最新審判情報を呼び出し元へ渡す。 |
| AutoRef | 課題 #78 に分割し、この変更の受入条件に含めない。 |

## 検証順序

機能単位では`TeamName`の既定値・非既定値、`TeamColor=BLUE`拒否、準備判定、再試行期限、最終送信後の確認猶予を検証する。起動制御の稼働経路で準備完了→欠落→復旧、永続不一致による期限超過、回復中断時の後始末、期待プロセス終了、所有者不一致を確認する。全体受入試験では移動前のチーム名、審判状態、移動距離、追跡入力、後始末を確認する。検証結果は対象`HEAD`とともに実績報告へ記録し、未実装の条件を受入成功として記載しない。

## 対象外

比較画面で扱うスナップショットの組、分割表示と重ね合わせ表示、数値差分の共有、時刻差表示、課題 #78 の試験専用AutoRef対策は対象外とする。依存追加、権限変更、ネットワーク設定変更、Game Controller/AutoRef本体の改変も対象外とする。

## 実行ごとの設定ファイル共有

AppHostは設定の優先順位に従って決めたチーム名と色を、実行識別子付きの設定ファイルへ原子的に出力する。CIと開発環境での全体受入では、AppHostと受入プロセスに同じ識別子と設定ファイルの場所を渡す。開発環境では実行ごとに別の場所を割り当て、過去のファイルを再利用しない。受入試験は設定ファイル内の識別子一致を必須とし、欠落、破損、不正値、別の実行向けのファイルを拒否する。
